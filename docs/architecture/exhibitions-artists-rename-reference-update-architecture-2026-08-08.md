# Exhibitions / Artists Rename Reference Update Architecture

| Property  | Value                                                                      |
| --------- | -------------------------------------------------------------------------- |
| Status    | Approved; Exhibitions first safe slice implemented, Artists deferred       |
| Date      | 2026-08-08                                                                 |
| Scope     | Exhibitions and Artists Content ID Rename with bounded reference updates   |
| Preserved | Asset bytes/paths, Delete, Production loaders/consumers, canonical content |

## Decision

Exhibitions and Artists may be renamed only by a collection-owned reviewed-plan
operation that moves one flat canonical Markdown file and rewrites the complete,
bounded set of typed incoming references. The operation is one logical
cross-file transaction. A source move without every required reference edit,
or a partial reference edit without the source move, is never a valid result.

The Exhibitions first safe slice now supplies the reviewed plan/execute API,
workspace UI, bounded News-link rewrite, transaction evidence, exact rollback,
and evidence-bound Publish set described below. Artist Rename remains deferred.
There is no schema or Production loader change, and canonical production
content/assets are unchanged by the implementation milestone. Works Rename and
all Works Asset Lifecycle v2 Content-ID and lock semantics remain separate.
Delete remains unchanged.

## Audited current boundaries

- Exhibitions and Artists use flat files at
  `src/content/<collection>/<content-id>.md`; the filename is the current
  Content ID and `/exhibitions/<id>` or `/artists/<id>` is derived from it.
- Astro's current flat `glob()` entries expose the filename as `entry.id`.
  Production routes, maps, JSON-LD, relationship resolution, and derived links
  currently consume that value. Rename must preserve this current behavior;
  it does not migrate consumers to the target `data.contentId` architecture.
- Editor readers retain exact `raw` bytes and parse strict collection schemas.
  Existing serializers can reproduce semantic edits but may reorder or
  normalize YAML. The Rename rewriter must therefore be a dedicated
  field-targeted YAML document editor; it must not route unrelated files
  through the ordinary full-draft serializer.
- `reference("artists")` and `reference("works")` are Production typed
  references. Editor schemas represent the same values as `{ id, collection }`
  and serializers store scalar IDs.
- Backup generations already include `src/content/`, `public/images/`, and
  `.kiki-editor/`. Rename evidence and recovery bytes under `.kiki-editor/` are
  therefore inside the existing backup boundary. Rename does not itself create
  a backup or weaken retention/hold rules.

## Authoritative dependency map

### Exhibition target

| Direction | Owner and field                                                                            | Meaning during Exhibition Rename                                                             |
| --------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| Incoming  | News `link` equal to `/exhibitions/<old-id>` with an optional trailing slash               | Required rewrite to the same form with `<new-id>`                                            |
| Incoming  | Structurally parsed Markdown link to the exact old Exhibition route                        | Human-reviewed required rewrite when the parser can preserve the link form; ambiguity blocks |
| Outgoing  | Exhibition `artists[]`                                                                     | Immutable; still points to the same Artists                                                  |
| Outgoing  | Exhibition optional `works[]`                                                              | Immutable; still points to the same Works                                                    |
| Derived   | Exhibition index/detail, Home exhibition cards, Artist detail derived exhibitions, JSON-LD | No file edit; route and lookup change follow the renamed canonical ID                        |
| Asset     | `hero.image` and body image nodes                                                          | Byte- and path-identical; never moved or renamed                                             |

There is no structured Exhibition-ID reference in Artists, Works, Home, or
Journal. A News link is typed for Rename only when it parses as the exact known
internal Exhibition route. Query strings and fragments are not part of the
current recognized News image route and therefore block rather than being
silently rewritten. External URLs, generic paths, prose, JSON-LD generated by
Production, and Editor URLs are not incoming canonical references.

### Artist target

| Direction | Owner and field                                                                                               | Meaning during Artist Rename                                                                 |
| --------- | ------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Incoming  | Every Work `artist`                                                                                           | Required scalar-ID rewrite from old to new                                                   |
| Incoming  | Every Exhibition `artists[]` element                                                                          | Required scalar-ID rewrite from old to new, preserving order                                 |
| Incoming  | News `link` equal to `/artists/<old-id>` with an optional trailing slash                                      | Required rewrite to the same form with `<new-id>`                                            |
| Incoming  | Structurally parsed Markdown link to the exact old Artist route                                               | Human-reviewed required rewrite when the parser can preserve the link form; ambiguity blocks |
| Outgoing  | Artist optional `works_layout[].works[]`                                                                      | Immutable; these are Work IDs, not Artist IDs                                                |
| Derived   | Artist index/detail, Work detail Artist link, Exhibition Artist links/names, Home Artist story image, JSON-LD | No direct edit; route and relationship resolution follow updated canonical references        |
| Asset     | Artist `hero.image`, Work `images[].src`, Exhibition hero/body images                                         | Byte- and path-identical; names resembling the old Artist ID are ownership hints only        |

Exhibition membership is owned by `Exhibition.artists`; Work ownership is owned
by `Work.artist`; Artist owns only curated Work order/layout. Artist Rename
updates the two owning incoming fields and does not manufacture reciprocal
fields or reorder either collection.

### Excluded and human-reviewed references

The plan inventories but never automatically changes external URLs, prose,
unrecognized internal paths, asset paths, Home `sections[].href`, Work inquiry
URLs, Astro `entry.id` strings outside canonical content, generated Production
markup, or source-code literals. Recognized Markdown links are always displayed
as individual human-reviewed edits with file and node location. If a Markdown
parser cannot identify and rewrite a link without changing unrelated bytes,
Rename is blocked; there is no raw substring replacement or force mode.

## Collection-owned reference inventory and rewrite

Planning scans every regular, non-symlink canonical file in Artists, Works,
Exhibitions, News, Home, and every complete Journal Content Unit. It rejects an
unsafe root, unexpected file type, unreadable file, parse failure, structural
schema failure, or incomplete Journal unit because the graph is then unknown.

The inventory uses these adapters:

1. Works parser: `artist` only.
2. Exhibitions parser: `artists[]` only for Artist Rename; `works[]` remains
   validation context.
3. News parser: exact normalized `/artists/<id>` and `/exhibitions/<id>` route
   forms only.
4. Markdown parser: link destinations only, never prose or code, for exact
   recognized public detail routes.
5. Relationship validator: all Artist/Work and Exhibition/Artist/Work existence,
   ownership, membership, duplicate, and layout-cardinality rules against the
   complete prospective graph.

Each discovered item records collection, Content ID, repository-relative file,
field/node path, old typed target, proposed target, original byte hash, and the
specific adapter/schema version. Duplicate references in one file are separate
inventory items but produce one prospective file.

The dedicated rewriter edits only scalar spans proven by the parser. It retains
all bytes outside those spans, including key order, comments, quoting, line
endings, blank lines, body text, and final newline. Replacements are applied
from the last byte offset to the first. The result is reparsed and must differ
from the preimage only at the reviewed spans. If byte-span preservation cannot
be proven, the plan is blocked rather than normalizing the complete file.

## Reviewed plan

The server returns a deterministic plan containing:

- operation ID, operation kind, schema/policy/adapter versions, plan hash, UTC
  creation time, repository realpath, branch, HEAD, upstream identity, and
  repository-wide lifecycle-lock status;
- collection, old/new Content IDs, exact old/new canonical paths, old/new public
  routes, source SHA-256 and byte size, and destination absence plus case-fold
  collision proof;
- every reference edit grouped by file, with owner collection/ID, field or node
  path, old/new typed value, old/new route, source hash, resulting hash, and a
  concise byte-preserving diff;
- an explicit unchanged section for outgoing references, assets, Production
  behavior, and policy-excluded/human-reviewed observations;
- complete touched-path order, preimage hashes, prospective hashes, validation
  results, warnings about old external URLs, and all blockers; and
- Publish preview: old target path deletion, new target path addition, every
  modified reference path, and the fact that publishing is a later action.

The UI must present identity/route changes first, then reference edits grouped
by owning file, then unchanged/excluded observations, validation, and exact
Publish paths. Execution requires explicit confirmation of the exact plan hash
and old/new IDs. Dirty or pending workspace state blocks planning and execution.
The browser displays server facts and never computes references or safety.

## Canonical reread and drift detection

Planning reads bytes through safe file handles, computes SHA-256 and size, and
parses those same bytes. It records absence tokens for the new target and every
temporary/recovery destination. Immediately before execution, under the owned
content-lifecycle lock, the server rebuilds the entire plan from canonical
state and requires an identical plan hash.

Execution then opens and verifies every existing path again before its first
mutation. Any changed byte, file type, symlink status, inode replacement that
invalidates the safe handle, branch, HEAD, upstream, destination, case-fold
name, reference graph, policy version, or lock state is `plan-stale`; the
operator must review a new plan. mtime alone is never identity. New unrelated
canonical files also invalidate the complete graph inventory.

After staging, all prospective files are read from the transaction area using
collection-owned schemas and the same reference inventory. The old target must
be absent from every explicit typed reference and recognized old route; the new
target must exist exactly once; all relationship and route rules must pass.
After installation, canonical readers repeat those checks at the real roots,
the renamed source must expose the new Content ID, and every installed byte must
match its prospective SHA-256.

## Atomic staging and installation

Rename uses a same-filesystem transaction directory under `.kiki-editor/` and
a durable operation journal written before canonical mutation. The journal
contains all preimages byte-for-byte, modes, hashes, safe canonical paths,
prospective bytes, completed step markers, and the intended next step.

Deterministic steps are:

1. Acquire the repository-wide content-lifecycle lock and reject any active or
   unverifiable Asset Lifecycle v2 repository lock.
2. Rebuild and match the reviewed plan; create and fsync evidence/recovery
   records and all prospective files with exclusive creation.
3. Validate the complete prospective repository graph from the staged overlay.
4. For each touched existing path in sorted repository-relative order, move the
   exact baseline file to its transaction-owned recovery path without overwrite.
5. Install rewritten reference files at their original paths, then install the
   renamed source only at the new path, all without overwrite.
6. Canonically reread and verify the complete installed graph and exact hashes;
   record `completed`, release the lock, and return the new saved-unpublished
   workspace.

The filesystem cannot make this multi-file change externally atomic. Safety is
provided by exclusive mutation authority, durable intent/preimages, no-overwrite
steps, fail-closed readers while an operation is incomplete, and deterministic
rollback. Save, Create, Publish, another Rename, and future Delete must all
respect the same content-lifecycle lock.

## Rollback and recovery

Any failure after the first canonical move enters rollback. In reverse install
order, rollback removes an installed prospective file only when its current
bytes and mode match the journal, then restores each preimage only when its
canonical destination is absent. The new renamed path is removed only when it
is the exact transaction-owned prospective source. Every restored file is
reread and compared byte-for-byte, including line endings and final newline,
and the complete original reference graph is revalidated.

Successful rollback records `rolled-back`, restores every touched canonical
file byte-for-byte, removes only transaction-owned staging bytes, and releases
the lock. Any external change, missing recovery byte, hash mismatch, destination
occupation, incomplete journal, or failed original-graph validation records
`manual-recovery-required`; it preserves the lock, journal, recovery bytes,
staging bytes, and canonical stop state. Restart inspection resumes or rolls
back only idempotent journaled steps and never guesses ownership.

## Publish contract after Rename

Rename itself never stages, commits, pushes, or deploys. A successful operation
returns a saved-unpublished workspace at the new Content ID. Publish must be
expanded in the later implementation milestone to recognize exactly one
pending Rename transaction and independently rebuild canonical/Git state.

For either collection, the Publish set is exactly:

- deletion of `src/content/<target-collection>/<old-id>.md`;
- addition of `src/content/<target-collection>/<new-id>.md`; and
- modification of every reference file listed by the completed Rename evidence.

Publish requires a clean pre-existing index, matching branch/upstream, matching
completed evidence, exact canonical hashes for all new/modified files, exact
Git-HEAD blobs for all old/preimage files, and no extra worktree path in the
operation boundary. It stages the explicit old/new/reference path list with
rename detection disabled for verification, then proves: old index entry
absent, new blob exact, every modified reference blob exact, and no staged path
outside the reviewed set. Repository-wide tests, Astro check, and Production
build run before commit/push. A reference file with other unstaged edits or a
missing/extra pending path blocks Publish; Publish never merges them.

The commit message identifies the target collection and new ID. Push failure
retains the existing `committed-push-failed` terminal behavior. Evidence and
recovery files under `.kiki-editor/` are never staged or consumed by Production.

## Stable states and guidance

| Code                            | Meaning and operator guidance                                                                                             |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `invalid-content-id`            | Old/new ID is invalid. Enter a lowercase hyphenated ID.                                                                   |
| `source-unavailable`            | Source is missing, invalid, unsafe, or a symlink. Repair canonical content and request a new plan.                        |
| `destination-conflict`          | Exact or case-fold destination exists. Choose another ID.                                                                 |
| `reference-graph-incomplete`    | A canonical unit, typed field, Markdown link, or route cannot be safely inventoried. Repair it; no force mode exists.     |
| `reference-rewrite-unsupported` | A recognized incoming reference cannot be byte-preservingly rewritten. Resolve it manually before replanning.             |
| `prospective-validation-failed` | The proposed graph violates schema, existence, ownership, membership, duplication, or route rules. Review listed files.   |
| `plan-stale`                    | HEAD, branch, bytes, destination, graph, policy, or repository state changed. Review and confirm a fresh plan.            |
| `workspace-dirty`               | Save or discard current draft changes before planning/executing Rename.                                                   |
| `lifecycle-lock-conflict`       | Another content or asset lifecycle operation owns or has uncertain lock state. Reconcile its evidence first.              |
| `unsafe-repository`             | Root, upstream, path, file type, symlink, staging/recovery path, or Git state is unsafe. Stop and inspect.                |
| `rename-failed-rolled-back`     | Execution failed and all original bytes were restored. Inspect evidence and request a fresh plan.                         |
| `manual-recovery-required`      | Exact rollback cannot be proven. Preserve the lock/evidence and perform operator recovery; all mutation remains disabled. |
| `publish-set-mismatch`          | Git/canonical paths or blobs differ from completed evidence. Do not stage partially; reconcile and retry.                 |
| `committed-push-failed`         | Local commit exists but push failed. Retry the existing push recovery flow; do not rerun Rename.                          |

## Implementation gates and acceptance

Artists implementation remains deferred until a separate milestone supplies
collection-owned inventory/rewriter modules, the staged-overlay validator,
durable journal/restart inspection, composed lock enforcement, UI/API, and
Publish expansion. Tests must use isolated Git repositories and cover every
reference class, multiple edits per file, formatting preservation, new files
during planning, every mutation-step failure, exact rollback, rollback refusal,
restart at every journal state, and exact Publish staging.

Acceptance must also prove that canonical asset bytes and paths are unchanged,
Works Asset Lifecycle v2 state is unchanged, Delete and Production loaders are
unchanged, the production route count changes only as the old target route is
replaced by the new target route, and no implementation endpoint exists in this
documentation milestone.
